# Cross-Platform Design System Rules

## Purpose

This file defines cross-platform page design rules for Yeepay business systems generated by this skill.

Platform-specific color, layout emphasis, navigation style, and domain component rules must come from `specs/themes/{theme}.md`.

Do not bind a generated page to a platform only from this file. Always combine this file with the selected theme spec.

## Theme Boundary

- Use this file for shared page structure, interaction, accessibility, and component composition rules.
- Use `specs/themes/boss-ledger.md` for Boss Ledger operational admin pages.
- Use `specs/themes/yeepay-开放平台-DESIGN.md` for YOP / YeePay Open Platform, developer center, API documentation, and product documentation pages.
- Do not mix different platforms' primary colors, page density, navigation patterns, or exclusive component rules.

## Design Tone

Business pages should be clear, predictable, and task-oriented.

Avoid decorative layouts, oversized hero sections, visual effects that reduce readability, and page structures that hide primary workflows.

## Layout

- Use a clear page title and concise subtitle only when needed.
- Put high-frequency controls near the top.
- Use full-width content areas with responsive constraints.
- Prefer the page template selected from `specs/page-templates.md`.
- Use drawers or modals for focused create, edit, detail, and review tasks.
- Keep cards for grouped metrics, repeated objects, or modal content.
- Do not nest cards.
- Keep navigation, filtering, table, form, and action areas visually distinct.

## Visual Rules

- Use restrained color and follow the selected theme palette.
- Use status colors consistently: success, warning, error, processing, default.
- Use typography hierarchy through size and weight, not decoration.
- Use consistent spacing steps.
- Keep border radius small and aligned with Ant Design defaults.
- Ensure text does not overflow buttons, table cells, cards, or form controls.
- Keep icon usage consistent with the selected platform and component context.

## Interaction Rules

- Make primary actions obvious and singular per workflow.
- Keep destructive actions visually separated and confirm before execution.
- Use progressive disclosure for advanced filters and secondary fields.
- Prefer inline table actions for row-specific operations.
- Use batch actions only when they are clearly required.
- Preserve user context after search, pagination, sorting, submit, and mutation actions.
- Provide clear feedback for loading, success, failure, empty data, and permission limits.

## Accessibility

- Preserve keyboard-accessible controls.
- Use readable labels instead of icon-only controls unless the icon is standard and has a tooltip.
- Maintain sufficient contrast for text and status indicators.
- Ensure forms, filters, table actions, drawer actions, and modal actions have clear accessible names.
