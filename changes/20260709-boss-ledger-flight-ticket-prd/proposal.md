# Proposal: Boss Ledger 机票业务运营后台 PRD

## 1. Original Request

`/yeepay:prd 输一个机票业务的prd`

## 2. Requirement Understanding

本次需求是产出一份面向机票业务的产品需求文档。由于用户未指定是 C 端购票产品、商户开放平台能力，还是后台运营页面，按 Yeepay Page Skill 默认规则选择 Boss Ledger 运营后台场景，围绕机票订单、出票、退票、改签、航变通知、供应商对账和异常处理设计一套可评审、可继续拆解为页面设计与研发任务的 PRD。

## 3. Target Theme

- Theme: Boss Ledger
- Reason: 用户未指定 YOP / 开放平台 / API 文档等开发者平台关键词；“机票业务 PRD”可落到运营后台的订单、出票、退改签、对账与异常处理，按主题选择规则默认使用 Boss Ledger，并在“合理假设”中说明。

## 4. Background

机票业务链路涉及搜索报价、下单占座、支付、出票、退改签、航变通知、供应商结算和客诉处理。对于航旅运营团队，订单状态多、供应商时效差异大、退改签规则复杂，若缺少统一运营后台，容易出现出票超时、退款漏处理、航变未触达、供应商账款核对困难等问题。

本 PRD 目标是定义一个 Boss Ledger 机票业务运营后台的核心能力范围，使运营、客服、财务和风控人员可以在同一工作台内完成机票订单查询、出票监控、退改签处理、航变协同和供应商对账。

## 5. Goals

- 提供统一的机票订单查询入口，支持运营按订单号、乘机人、航班、航司、供应商、支付状态和出行日期快速定位订单。
- 建立出票监控机制，识别待出票、出票中、出票失败、出票超时和人工介入订单，降低漏出票风险。
- 支持退票、改签和取消订单的处理闭环，明确申请、审核、供应商处理、差额支付 / 退款和结果通知状态。
- 汇聚航变通知和影响订单，支持运营确认航变、触达用户、发起退改签处理。
- 提供供应商对账视图，支持按供应商、航司、交易日期和结算状态核对采购金额、退票款、改签差额和服务费。
- 对高风险操作增加权限和二次确认，避免误出票、误退款、重复处理和越权导出。

## 6. Users / Roles

- 航旅运营人员：查询订单、监控出票、处理异常、跟进航变和供应商处理进度。
- 客服人员：查询用户订单、协助退票 / 改签 / 取消、查看通知记录和处理客诉。
- 财务人员：核对采购款、退款、改签差额、平台服务费和供应商结算状态。
- 风控人员：查看异常支付、频繁退改、黑名单乘机人或疑似套利订单。
- 系统管理员：维护供应商、航司、权限、导出能力和高风险操作开关。

## 7. Scope

### In Scope

- 机票订单查询列表：查询、重置、查看详情、下载Excel、列设置、订单状态筛选。
- 出票监控：待出票、出票中、出票失败、出票超时、人工介入订单识别和处理。
- 退改签处理：退票申请、改签申请、取消订单、审核、供应商处理、退款 / 补差结果记录。
- 航变协同：航班变更通知、影响订单列表、用户触达状态、可退改处理入口。
- 供应商对账：供应商订单、采购金额、退票款、改签差额、服务费、结算状态和差异标记。
- 权限规则、状态规则、异常场景和验收标准。
- 生成 Product Only 产物：`proposal.md` 和 PRD 摘要 `preview.html`。

### Out of Scope

- C 端机票搜索、比价、选舱、乘机人录入、在线支付等前台购票页面。
- 真实航司 / GDS / NDC / OTA / 供应商接口联调。
- 真实出票、退票、改签、航变通知和短信 / 邮件 / App Push 发送服务。
- 真实财务结算、发票、资金清分和供应商付款流程。
- 正式 React + TypeScript 生产工程代码。
- 完整风控策略模型、黑名单系统和审批流配置后台。

## 8. Business Object

机票订单、航段、乘机人、支付单、出票单、票号、退票申请、改签申请、航变通知、供应商订单、供应商账单、退款单、改签差额单、操作日志、通知记录、异常工单。

## 9. Core Workflow

1. 运营人员进入 Boss Ledger 机票业务运营后台，默认进入机票订单查询列表。
2. 用户通过订单号、乘机人手机号、乘机人证件号、航班号、航司、供应商、订单状态、出票状态、出行日期等条件查询订单。
3. 系统展示订单列表、关键金额、状态、航段、乘机人、供应商和操作入口。
4. 对待出票或出票异常订单，运营进入详情抽屉查看支付、占座、供应商返回和出票日志，并执行重试出票、转人工或取消订单。
5. 对退票 / 改签申请，客服或运营进入处理抽屉，核对规则、手续费、差额、供应商状态和用户确认结果后提交处理。
6. 对航变通知，运营查看影响订单，确认用户触达结果，并根据规则发起免费退票、免费改签或继续出行处理。
7. 财务人员进入供应商对账视图，按供应商和日期核对采购、退款、改签差额和服务费，标记差异并下载对账明细。
8. 高风险操作触发二次确认，系统记录操作人、操作时间、操作前后状态和失败原因。

## 11. Status

| Status | Meaning | Available Actions |
|---|---|---|
| 待支付 | 用户已创建订单但未完成支付 | 查看详情、关闭订单 |
| 已支付 | 用户已支付，等待占座或出票 | 查看详情、发起出票、取消订单 |
| 待出票 | 支付成功且满足出票条件，等待供应商出票 | 查看详情、重试出票、转人工 |
| 出票中 | 已向供应商提交出票请求，等待返回结果 | 查看详情、刷新状态、转人工 |
| 出票成功 | 票号已生成，订单可正常出行 | 查看详情、申请退票、申请改签、下载行程单 |
| 出票失败 | 供应商出票失败或返回异常 | 查看详情、重试出票、转人工、取消订单 |
| 出票超时 | 超过约定出票时效仍未返回终态 | 查看详情、刷新状态、转人工、通知客服 |
| 退票待审核 | 用户或客服已提交退票申请，等待审核 | 查看详情、审核通过、审核驳回 |
| 退票处理中 | 已提交供应商退票，等待退款规则和结果 | 查看详情、刷新状态、转人工 |
| 退票完成 | 退票处理完成，退款状态已同步 | 查看详情、下载凭证 |
| 改签待确认 | 用户已提交改签需求，待确认航班和差额 | 查看详情、确认改签、取消申请 |
| 改签处理中 | 已提交供应商改签，等待结果 | 查看详情、刷新状态、转人工 |

| 航变待处理 | 航司发生航变且影响订单尚未处理 | 查看详情、通知用户、发起退票、发起改签 |

## 12. Permissions

- 订单查看：航旅运营、客服、财务、风控可按授权范围查看订单；证件号、手机号等敏感字段默认脱敏。
- 敏感信息查看：查看完整手机号、完整证件号需要客服主管、运营主管或风控权限，并记录查看日志。
- 出票操作：重试出票、转人工出票、取消已支付订单仅航旅运营人员可操作，出票成功后不得重复出票。
- 退改签处理：退票审核、改签确认、手续费调整由客服主管或运营主管操作；驳回必须填写原因。
- 退款相关操作：触发退款、调整退款金额、处理重复退款风险需要二次确认，正式系统可叠加审批或密码校验。
- 供应商对账：财务人员可查看和下载对账数据；运营只可查看订单级对账状态，不可确认结算。
- 导出权限：订单明细、乘机人信息、供应商账单下载需要导出权限；导出文件应记录操作日志。
- 系统配置：供应商、航司、退改签规则和高风险操作开关仅系统管理员可维护。

## 13. Edge Cases

- 查询无结果时，列表展示 Ant Design Empty 空状态，并保留当前筛选条件。
- 供应商出票接口超时但后续返回成功时，系统应防止重复出票，并提示状态已更新。
- 支付成功但占座失败时，订单进入异常队列，允许运营取消订单并触发退款。
- 出票成功后用户继续发起取消订单时，系统应引导走退票流程，不允许直接取消。
- 退票审核驳回未填写原因时，系统阻止提交并提示填写驳回原因。
- 改签差额为补收时，未完成差额支付不得提交供应商改签。
- 航变通知重复推送时，同一订单只保留最新航变处理状态，并记录历史通知。
- 用户联系方式缺失或短信发送失败时，系统应标记触达失败并允许人工备注。
- 供应商账单金额与平台订单金额不一致时，系统标记对账差异，禁止直接确认结算。
- 用户无权限访问完整证件号或导出数据时，操作不可见或置灰并提示权限不足。
- 订单状态被他人更新时，当前操作提交失败并提示刷新后重试。
- 网络错误或后台服务异常时，保留当前页面上下文并展示错误反馈。

## 14. Acceptance Criteria

- 当运营人员输入订单编号并点击“查 询”时，系统应返回匹配的机票订单记录。
- 当运营人员选择出票状态为“出票失败”并点击“查 询”时，系统应仅展示出票失败的订单。
- 当查询条件无匹配数据时，表格区域应展示空状态，不应清空筛选条件。
- 当运营人员点击订单“查看”时，系统应打开详情抽屉，展示订单、航段、乘机人、支付、出票、退改签和操作日志信息。
- 当待出票订单点击“重试出票”时，系统应展示二次确认；确认后订单进入出票中并记录操作日志。
- 当订单已出票成功时，系统不应展示“取消订单”操作，应展示退票和改签入口。
- 当客服提交退票驳回且未填写驳回原因时，系统应阻止提交并提示“请输入驳回原因”。
- 当改签申请存在补收差额且用户未支付时，系统应禁止提交供应商改签。
- 当航变通知影响订单时，系统应展示航变类型、原航班信息、新航班信息、用户触达状态和可执行处理操作。
- 当财务人员查看供应商对账时，系统应按供应商和交易日期展示采购金额、退款金额、改签差额、服务费和结算状态。
- 当平台金额与供应商账单金额不一致时，系统应标记“对账差异”，并禁止直接确认结算。
- 当无导出权限用户进入页面时，下载Excel操作应不可见或不可点击，并给出权限不足反馈。
- 当有权限用户点击“下载Excel”时，系统应按当前筛选条件生成导出任务并记录导出日志。
- 当系统接口失败时，页面应展示失败反馈，并允许用户保留筛选条件后重试。

## 15. Assumptions

- 用户明确给出的信息只有“机票业务的 PRD”。
- 因未指定平台，本 PRD 默认面向 Boss Ledger 后台运营人员，而不是 C 端购票页面或 YOP 开放平台 API 文档。
- 业务按“平台自营 / 聚合供应商出票”的航旅机票经营模型设计。
- 当前业务日期按工作区日期使用 2026-07-09。
- 退票、改签、航变和供应商对账规则仅定义产品流程与字段，不代表真实航司或供应商接口规则。
- 敏感数据展示、导出、退款、出票重试等高风险操作在正式系统中应接入权限中心、操作日志和必要审批。
- `preview.html` 是 PRD 阅读和评审摘要，不是生产前端代码。
