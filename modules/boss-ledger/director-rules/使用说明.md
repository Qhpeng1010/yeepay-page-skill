# 老板管账导演规则使用说明

## 适用对象与目标

这份说明面向产品和设计同学。你的工作不是编辑生成后的页面代码，而是维护能长期影响同类页面的规则，并让系统只生成已经被允许、被验证的组合。

目录中的三个规则文件是给人读的设计决策；`execution/` 下的策略、规格和渲染器是系统执行这些决策的方式。不要改动页面预览目录里的 `preview-app.js`、`business.css` 或 `preview.html` 来“修复规则”，它们是构建产物。

## 先判断你要改哪一类内容

| 你的诉求 | 应修改的位置 | 例子 |
| --- | --- | --- |
| 所有页面都应使用同一视觉原则 | `01-visual-constitution.md` | 统一模块间距、表格密度、主按钮使用方式 |
| 某类业务应使用什么页面方案 | `02-template-application-rules.md` | 是否有来源上下文而应使用 Modal/Drawer；少字段独立任务何时应使用独立页 |
| 新增、调整或下线逻辑模板 | `02-template-application-rules.md` 的“可编译逻辑模板目录” | 新增 `form.review-page`，或修改 `detail.record` 的选择条件 |
| 用户操作、异常与成功反馈应如何表现 | `03-interaction-acceptance-rules.md` | 重置是否保留条件；危险操作确认必须说明什么 |
| 仅这个新页面的字段、数据、文案或默认值 | 当前 Change 的 `page-spec.json` | 增加“代理名称”查询条件、调整列表列顺序 |
| 系统是否已允许生成某个能力 | `../execution/generation-policy.json` | 是否开放 Dashboard、步骤表单或嵌入式详情 |

## 手工修改规则的流程

1. 先写清楚问题、适用范围和一个具体反例。例如：“列表页的操作列不能被用户隐藏，否则无法处理记录”。
2. 选择上述三个规则文件中唯一合适的位置。若它是跨页面、会重复出现的原则，才写入导演规则；单页需求只写入 Page Spec。
3. 新增或调整规则时保留原有 Rule ID；新增硬规则使用下一个对应前缀编号，例如 `BL-VIS-018`、`BL-TPL-019` 或 `BL-INT-015`。
4. 为硬规则补一个验收场景：前置条件、用户操作和可观察证据。交互类规则写入 `03-页面交互与验收规则` 的验收表。
5. 修改视觉 Token 或逻辑模板目录后，运行规则编译命令。它会自动更新主题、逻辑模板注册表和 Context Pack；不要手改 JSON、CSS 或 JavaScript 生成物。
6. 请 AI 或研发同学将新增硬规则对应到允许能力、Page Spec 校验和自动测试。规则文件本身说明设计意图，不能单独创造系统尚未支持的组件能力。
7. 更新发布清单并运行完整检查。发布清单会记录规则版本；未更新时系统应拒绝交付。

## 如何使用规则生成一个页面

以“商户查询”为例：

1. 提交业务需求：对象、用户、查询条件、列表字段、要执行的操作和风险。
2. 系统先选择页面家族和逻辑规则模板。查询、比较多条记录会进入列表家族；规则模板只描述选择与组合边界，不包含坐标、样式或页面代码。
3. 系统读取当前已开放的能力。普通查询列表已默认开放；`shadow` 组合必须明确引用已验证组合 ID；Dashboard、独立结果页等仍会报告能力缺口或走旧路径。
4. AI 只填写 `page-spec.json`：页面名称、已选规则模板、运行模式、字段、数据列、状态和已允许的能力，并引用对应 Rule ID。
5. 固定渲染器生成实际页面，固定 Shell、组件和样式不允许被单页手改。
6. 系统检查规格、规则版本、生成文件一致性和浏览器表现；失败时返回具体规则或能力缺口。

## 你可以直接给 AI 的需求写法

```text
老板管账 / 商户管理：新增商户查询列表。
用户：运营人员。
任务：按商户名称、商户编号和部门查询，并查看详情。
列表：商户编号、商户名称、部门、直属代理、状态、注册时间。
操作：详情；停用属于危险操作，需要说明对象、影响和停用后的状态。
请按导演规则选择页面家族；若组合未开放，请输出能力缺口，不要自由拼页面。
```

## 不要这样修改

- 不要在生成后的预览 HTML、JS 或 CSS 上直接修补通用问题。
- 不要为了完成需求，把 `pending`、`legacy` 或 `workflow-only` 能力伪装成已经支持的 Page Spec。
- 不要删除 Rule ID，也不要用模糊原则替代可验收的规则。
- 不要把一次性字段文案写进视觉宪法。
- 不要把历史页面当作规则来源；历史页面只可作为参考和回归样例。

## 发布前最小检查

规则修改后，请让 AI 或研发同学依次执行：

```bash
node scripts/build-boss-ledger-context-packs.mjs
node scripts/check-boss-ledger-generation-policy.mjs
node scripts/refresh-boss-ledger-release-manifest.mjs
node scripts/verify-boss-ledger-release-manifest.mjs
node scripts/validate-boss-ledger-page-spec-system.mjs
```

全部通过，规则才可以作为当前版本的有效生成依据。若只是编辑单页 `page-spec.json`，运行该页面对应的 Page Spec 构建和验证即可。
